# Changelog

All notable changes to Prune are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses
[Semantic Versioning](https://semver.org/).

## [Unreleased]

## [0.1.2] - 2026-09-22

The interface, laid out as a utility rather than as an administration console. Nothing about
what Prune finds or removes has changed.

### Changed

- The column of eight labelled destinations down the left is now a thin strip along the top. A
  sidebar makes every screen feel like a page in a site; a utility is something you point at a
  machine, so there is one place to stand and the rest stays out of the way.
- The home screen is one figure and one action — how much can be reclaimed, at a size you can
  read across a desk, with the button under it. It was previously three equal panels of live
  readings, a list and a history box, each bordered and shadowed alike, so nothing was more
  important than anything else and the only action was a small button in the corner of a card.
  The live readings are now a quiet line at the foot, where context belongs.
- Cards lost their shadow and softened their border, which was most of why every box on every
  screen carried the same weight.
- The cleaner's three separate clusters of controls became one bar, and the button that starts
  the work carries the number that makes it mean something: "Review 6 · 7.37 GB" rather than a
  bare "Review" beside a "Found 10.6 GB" label. Its rows, and the process table's, have room to
  be read rather than being packed like a spreadsheet.
- Startup no longer spends its right-hand column — where a row puts what you act on — on
  whether an item is a launch agent or a launch daemon.
- A disk scan reports its total first instead of chaining the total, the file count, the folder
  count and the scan duration together as though they mattered equally.

## [0.1.1] - 2026-09-22

A packaging fix. Nothing about what Prune does has changed; if 0.1.0 is installed and running,
there is no reason to hurry.

### Fixed

- The macOS disk image demanded that the MIT licence be agreed to before it would mount. `licenseFile` applies to every bundle at once — there is no per-installer setting in Tauri 2 — and on macOS that becomes a modal agreement, so `hdiutil attach` on the published `.dmg` answered "attach canceled" and any scripted install, Homebrew casks included, stopped there. MIT grants rights rather than asking for assent, so presenting it as something to accept was wrong twice over. The licence still ships: in the repository, in the command-line archives, and named in the application's own copyright string.

## [0.1.0] - 2026-09-21

The first release. Everything below is what Prune does on day one — there is no earlier version
to have changed from, so the Fixed entries record defects found and corrected during development
rather than regressions anyone shipped.

### Fixed

- The desktop app and the command line were both called `prune`, so they overwrote each other in `target/`. Running `pnpm tauri build` and then `./target/release/prune scan` opened the GUI and ignored the arguments, and a release cut from one directory could have shipped the desktop app under the command line's name. The desktop binary is now `prune-desktop` and a check in CI refuses any future collision. The bundle is still `Prune.app` and the command is still `prune`.
- The uninstaller's own view had no tests, including for the behaviour that was fixed in it earlier: that data another installed copy is still using is named as shared rather than quietly offered. Seven now hold that, and that something marked protected cannot be chosen by clicking its row or its checkbox, that selecting everything selects only what may be removed, that the button says whether it is uninstalling or only clearing up after, and that removal is asked for exactly what was ticked.
- A failed cleanup was drawn in the colour of a successful one. The badge at the top of the result — the largest thing on screen, and often the only thing read — stayed green whatever happened, with only a small icon inside it changing. It now matches the outcome: green when everything went, amber when some of it did, red when none of it did.
- Stopping a process trusted that the id still meant what it did a moment ago. The engine already re-applied its protection rules for exactly that reason — "by the time it arrives that id may belong to something else entirely" — but an id recycled onto an *ordinary* process passes every one of those rules, so the user could confirm one program and watch a different one die. The name they were shown now travels with the request and is checked against the process that actually holds the id. A caller with no name to check, such as `prune processes --stop 1234`, is served as before.
- The confirmation dialog had no tests, and it is the last thing anyone reads before something is removed. Ten now hold what it promises: that it lists every target with its path, that a blocked item says why it was blocked rather than being left out, that items which can only be deleted outright are named even when the button says "Move to Trash", that permanent deletion is called irreversible, and that the dialog cannot be dismissed halfway through a removal.
- The browser providers had no tests, and they are the ones that work *inside* a profile — beside cookies, logins, history, bookmarks and site data. A single wrong entry in the cache list would have started removing any of it, with nothing to catch it. The list is now pinned by a test that lays out a realistic profile and fails, by name, if anything outside it is ever reported. Which platform's profile directories are used is also chosen by argument rather than by `cfg!`, so the Windows answer is reachable from a test on either machine.
- "Ask to quit" reported a refusal the system never made. Windows has no POSIX signals, so there is nothing polite to send, and the code read that absence as the process having refused — leaving the Monitor's gentler option failing with a misleading message. It now says what is actually true: asking is not available here, and forcing is the only way, which loses anything unsaved. It does not quietly force instead, because the label promised to ask.
- A test of the custom-provider path tokens wrote its fixture as Unix paths. `expand` refuses anything that is not absolute, which is what makes `relative/path` no location at all — and on Windows `/home/u` is not absolute, it is relative to the current drive. The engine was right to refuse it; the test was measuring its own fixture. It now builds paths from a root the running platform calls absolute.
- The command-line tests assumed macOS. The cache provider deliberately looks in different places per platform — a unified `Caches` directory on macOS, specific well-known locations under `%LOCALAPPDATA%` on Windows, which has no single cache directory — but the test fixture only ever laid out the macOS shape, so on Windows a scan correctly reported no application caches and three tests read that as a failure. The engine was right; the tests were not. They now lay out both, and the one asserting that Prune refuses to stop the init process accepts that Windows has no pid 1 to refuse.
- The Windows CI job could not run the IPC tests at all. `src-tauri` still carried Tauri's mobile crate types (`staticlib` for iOS, `cdylib` for Android) although Prune builds neither, and on Windows the `cdylib` made the integration test link against `prune_lib.dll`; the test binary then failed to start with `STATUS_ENTRYPOINT_NOT_FOUND` before a single test ran. A plain `rlib` is what both consumers want.
- Windows had no tests at all. It is an advertised platform, it builds in CI, and none of the logic deciding what an uninstall may delete was covered — while the same logic on macOS had a shared-folder rule and four tests behind it. One uninstall could have claimed `%LOCALAPPDATA%\\Programs`, where every per-user installation lives and which cannot be added to the protected list because those applications are exactly what the uninstaller is for, or a vendor folder such as `%APPDATA%\\Microsoft`, which holds Office templates, mail signatures and the Start Menu. Windows now has the same rule, and the rules are compiled and tested on every platform rather than only on the one they ship to.
- The README and the architecture document described a project several phases behind the one in the repository: the disk analyzer, uninstaller, startup manager and command line were all marked as planned or as a read-only prototype, and the prototype they named had been deleted. Every one of them ships. Also corrected: the risk table implied that everything below High Risk is pre-selected, when only `Safe` ever is.
- "Select safe items" ticked the Trash even when the mode was "Move to Trash". Items already in the Trash can only be deleted outright, so one irreversible item sat among a list the user had been told was recoverable. `prune clean` already refused this, with the reasoning written down; the desktop app now applies the same rule. Choosing "Delete permanently" is asking for exactly that, so there it is still included.
- Six locks in the command layer still panicked on a lock a previous panic had poisoned, including the one on the removal path — one bug in one action would have left cleaning broken until the app was quit and reopened. They recover like the rest, which is sound because everything they guard is a cache and every path is re-validated at the moment of deletion.
- Uninstalling one copy of an application could delete the data another copy was using. Keeping `App-v1.2-backup.app` beside `App.app` is ordinary, and both read the same caches, preferences and application support, because those are keyed by bundle identifier rather than by which file was launched — so Prune offered the same leftovers under both, and removing the backup would have taken the working copy's settings with it. Found on a real machine, where two copies of one application shared every leftover. The leftovers are now reported as protected while more than one copy is installed, with the other copy's location named; once it is gone, a rescan offers them normally.
- A disk analysis held far more memory than it needed. Every directory stored its full path, and a `HashMap<PathBuf, usize>` stored the same path again as a key — on a tree with a million folders, twice a million paths, kept for as long as the analysis was, and the app keeps the last three. Nodes now know only their name and their parent; a path is rebuilt by walking up, and a lookup walks down. Measured on a 7.2M-file tree: peak memory fell from 564 MB to 142 MB with no change in speed.
- The largest-files list kept a side table that could only grow: every file that was ever briefly in the top two thousand stayed in it. On a tree walked smallest-first that is one entry per file — hundreds of megabytes on a home directory, to produce a list of two thousand. The paths live in the heap now, so the memory is bounded by the size of the list.
- The interface had no live regions at all, so a screen reader user was told nothing when a command failed, nothing while a two-minute scan ran, and nothing when it finished. Failures are now announced, the scan progress bar reports its position, and a completed scan says what it found. A polite region names the place being searched and nothing more — the file count and current path change several times a second and would talk over everything else.
- An error from a timer could not be dismissed. The Monitor polls every two seconds, so an unreachable backend set the same message again the instant the toast was closed. Dismissing now remembers the message, and a different failure still speaks up. Escape closes it.
- The faintest text failed WCAG AA at 2.94:1 in light and 3.27:1 in dark, and it is not decoration — it carries file paths, dates and item counts. Every text colour now clears 4.5:1 against every surface it can sit on, in both themes, with the three levels of text kept visibly apart. A test reads the palette out of the stylesheet and checks every pair, so a future shade adjustment cannot quietly take a category of information below the line.
- Prune was one of the busiest processes in its own process list. A live snapshot enumerated every mounted volume and walked all 2,600 processes, and the Monitor asked for one every two seconds: 439ms of work per tick, most of it re-reading disk capacities that had not changed. Volumes are now read at most once every ten seconds (and immediately after anything is removed, which is the one moment a stale free-space figure would be obvious), the process table is reused for the count rather than walked again, and each refresh asks only for the fields that are displayed. A snapshot went from 439ms to under a millisecond, and a process listing from 140ms to 55ms.
- Polling stopped for a window nobody is looking at. Leaving Prune open behind another window kept it reading the machine every two seconds, which costs battery for a view that cannot be seen. It pauses when the window is hidden and takes a fresh reading the moment it comes back, so what appears is current rather than however old the last one was.
- `prune processes` reported every process at 0.0% CPU. A process's share is the work it did between two readings and a one-shot command only took one, so the "busiest first" order was quietly "largest first" instead. It now takes both readings.
- "No network" is now checked rather than asserted. `scripts/check-no-network.sh` fails the build if any HTTP client or TLS stack appears anywhere in the workspace, or if anything socket-capable at all appears in the engine, and prints the dependency path that introduced it; a test does the same for the interface, refusing `fetch`, websockets, remote imports and the usual analytics packages. It also corrected the claim it was meant to enforce: the engine has no network crate at all, and the desktop app carries `tokio` because Tauri's own runtime needs it — the single-instance handover uses a Unix socket or a named pipe, which is local IPC, not a network.
- A path approved for removal was only checked once. Validation resolves the folders above a target, but removal happens later — after a preview the user reads, and after every other item in the plan — and in between anything with write access to the home directory could replace one of those folders with a link pointing elsewhere; `remove_dir_all` would then walk through it. The route is now re-resolved immediately before removal and the removal is refused if it changed.
- Settings were written in place, which truncates the file first. A crash or a full disk in between left an empty file where the user's project folders had been, and the next start silently fell back to guessing. The new settings are written beside the old ones and renamed over them, so the file on disk is always one version or the other.
- The operation log grew without limit. It is one line per removal and nothing ever trimmed it, so a machine cleaned regularly for a year would carry a history that had to be read in full every time the log was opened. It is now capped, and passing the cap rewrites it with the newest thousand entries kept — the same way settings are written, so a failure mid-rewrite cannot lose the history.
- Typing in the results filter was sticky. At the scale a real machine produces — a hundred projects, five hundred artifacts — every keystroke re-rendered the entire list, because nothing below the filter field was memoised. The list now updates a beat behind the field rather than blocking it, the rows and project sections skip renders whose input has not changed, and each section watches only its own selected count rather than the whole selection. Measured on the same tree: the median keystroke fell from 35ms to 2ms and the worst from 157ms to 7ms, and in a production build a burst of thirteen keystrokes and a five-hundred-item select both stay under the browser's long-task threshold.
- One panic could leave the application broken until it was quit and reopened. Rust poisons a lock when a thread panics holding it, and every later use panicked in turn; the locks now recover, which is safe here because everything they guard is a cache of scan results and removal re-validates every path at the moment of deletion rather than trusting anything cached.
- A rendering error blanked the window with nothing to read and nothing to click. An error boundary now explains that nothing was removed and offers a way back.
- Prune refused to start when its data directory could not be used. A bundled app has no console, so it simply did not open and nothing explained why. Opening the operation log can no longer fail: the directory is created on first write, an unreadable history reads as empty, and the application starts either way — losing the history is a degraded state, not a reason to refuse to run.

- `prune clean` emptied the Trash while promising to move things there. Items already in the trash can only be deleted outright, so a run that reads as reversible must leave them alone; it now does, and says why instead of reporting "nothing to remove".
- Uninstalling an application could offer to delete a vendor folder several products share. Removing one Google application would have taken Chrome's profiles and Drive's data with it. Vendor folders are never claimed now, but the product folder inside one still is, so Google Chrome correctly reports `Application Support/Google/Chrome` and leaves `Application Support/Google` alone.
- Old installers no longer match `.zip` on Windows. A zip is as likely to be a download worth keeping as an installer.
- A cleanup that succeeded but could not be written to the operation log was reported as a failure. The files were already gone, so the user was told the opposite of what happened and might have run it again. The removal now succeeds and the result carries the logging problem, which the result dialog shows.
- Scan sessions, cleanup plans and disk analyses were kept for the life of the process. An analysis of a home directory holds one node per directory — tens of thousands on a real machine — so a session spent scanning a few times grew steadily. Only the most recent few are kept now.
- Revealing a path in the file manager accepted anything under `/private`, so `/etc/hosts` was refused while `/private/etc/hosts`, the same file, was allowed. The check now compares canonical paths against the directories Prune actually works in.
- The Cleaner and Developer sections share one selection, but the Review button built its plan from everything selected anywhere. Selecting in Developer and then reviewing in Cleaner produced a plan bigger than the number on the button. Each section now plans only what it shows.

### Added

- Tauri 2 + React + TypeScript + Tailwind foundation with dark/light theme and sidebar navigation (Phase 1).
- `prune-core` crate: safety policy (whitelisted roots + protected paths), size calculation, trash/permanent removal, parallel provider scanning with progress and cancellation, overlap de-duplication, JSON-lines operation log.
- Dashboard with live storage / memory / CPU and potential cleanup summary (Phase 2).
- Cleaner: application caches, logs, temporary files, Trash, old installers, Chromium-family and Firefox caches (Phase 3).
- Developer: npm, pnpm (store plus registry metadata and dlx), Yarn, Bun, node-gyp, Deno, Playwright, Puppeteer, Cypress, Electron, pip, uv, Gradle, Maven, Cargo, Go, NuGet, CocoaPods, Swift Package Manager, pub, RubyGems, Composer, JetBrains, Homebrew, Xcode DerivedData / Archives / Device Support, Simulator caches, and a project artifact finder (`node_modules`, `target/`, `build/`, `dist/`, Python caches, virtualenvs, …) (Phase 4).
- Disk analyzer: single-pass directory tree with drill-down, largest files with size filters, file type statistics, cancellable; large files feed the same preview → remove pipeline (Phase 5).
- Uninstaller: application discovery (macOS `.app` bundles, Windows uninstall registry), leftover data matched by bundle identifier and bundle name, sizes measured in parallel, and removal through the same preview pipeline. System applications are listed with a protected bundle so only their leftovers can go (Phase 6).
- Startup manager: launch agents and daemons on macOS (with launchd's override database deciding the real state), `Run` registry keys and Start Menu Startup folders on Windows. Toggling is reversible and writes only to the override database / `StartupApproved`; nothing is deleted and items shared by all users stay read-only (Phase 7).
- Docker: what it is holding (images, containers, volumes, build cache) and two conservative ways to reclaim space. This is the one cleanup that does not go through Prune's pipeline, because the data lives inside Docker rather than in files Prune may touch, so the exact command is shown before it runs and Docker's own output is shown afterwards. `docker system prune` is used without `-a` and never with `--volumes`, so images in use and all volumes survive.
- Monitor: CPU per core, memory, swap, disks, network throughput, and top processes. A process can be asked to quit or forced to stop, with the same rule as everywhere else — Prune refuses what it must not touch: the kernel and init, anything that holds the session together (WindowServer, loginwindow, Finder, lsass.exe, explorer.exe and friends), processes owned by another user, and itself. The rules are re-applied at the moment of stopping, not trusted from the caller, and are also available as `prune processes --stop`.
- Preview (dry run) → confirm → remove → operation log pipeline with `Move to Trash` / `Delete permanently` modes.
- A stopped scan now says its results are partial instead of presenting a smaller total as the whole picture.
- Releasing is documented and scripted: `scripts/set-version.sh` writes the version everywhere, and tagging builds the desktop bundles and the CLI for macOS and Windows into a draft release.
- Animation is switched off for anyone whose system asks for reduced motion. All of it is decorative: a spinner that does not spin still says "working".
- The window reopens where it was left, and a second copy hands over to the one already running instead of scanning the same machine twice.
- Cache locations can be added without rebuilding. `providers.json` in the application data directory is read at start-up and its entries join the built-in providers, with `~` and `{cache}`-style locations so one file serves both platforms. A file only chooses where to look: every path it produces goes through the same safety layer, ids cannot shadow a built-in one, and a malformed entry is reported rather than silently skipped, because a provider that quietly failed to load looks exactly like one that found nothing.
- The dashboard has an opinion. A "Worth a look" card reads the scan and names the few things a total cannot say — dormant projects and what they hold, what can go with nothing at stake, a single directory that dwarfs the rest — and each one opens the section where it can be acted on, already filtered. It counts only what that destination will show, so the headline, the button and the plan all agree. Nothing there removes anything.
- Project artifacts are grouped by the project they belong to, with how long since anyone worked on it. A real machine produced 797 artifact directories; as 112 project rows, sorted by size and marked when nothing has touched them in three months, the list becomes something a developer can act on. The project is the nearest ancestor holding a `.git` directory, so a monorepo's scattered build folders count as one project, and the date comes from that repository's own metadata — an unknown date is reported as unknown, never as very old.
- Scan results can be filtered by name, path or kind and narrowed to safe items only, and are listed biggest first. With thirty providers and hundreds of project artifacts, the list needed a way in.
- Dashboard's Review & Clean arrives with the safe items already ticked.
- Command palette (⌘K / Ctrl+K) and ⌘/Ctrl + digit shortcuts for every view.
- Project folders are configurable: the developer scan searches the folders you name instead of the ones Prune guesses, persisted in `settings.json` next to the operation log. Folders must be inside your home directory, since that is the only place Prune can remove anything, and an unusable setting falls back to the guessed folders rather than silently disabling the scan. The Developer view says which folders it is searching and whether they were guessed.
- Permission awareness on macOS: locations the OS hides (Trash, Safari data, Mail, Messages) are detected and reported with a banner and a shortcut to the Full Disk Access settings, instead of silently shrinking every scan total.
- The project artifact walker measures what it found in parallel as well, cutting that scan from ~145s to ~100s on a machine with 789 artifacts and 4.1M files.
- Directory sizing is split across threads: the tree is divided into at least 32 independent subtrees (descending up to four levels to find them) and walked in parallel, with hard links still counted once through a sharded inode set. On a 12-core machine a 622k-file pnpm store drops from ~50s to ~20s and a 368k-file Gradle cache from 38s to 23s, with byte-identical results.
- Frontend tests for the selection, preview, execute and cleanup-bookkeeping logic in every store, plus component tests asserting that a protected target can never be selected and that dialogs trap and restore focus.
- IPC integration tests on Tauri's mock runtime covering the real command surface, including a full disk scan → preview → execute → operation log cycle.
- A `prune` command line built on the same engine: `status`, `providers`, `scan`, `clean`, `disk`, `apps`, `startup` and `log`, each with `--json` for scripting and meaningful exit codes. `clean` is a dry run unless `--yes` is passed and never selects anything riskier than low on its own. The read-only example prototypes it replaces have been removed.
